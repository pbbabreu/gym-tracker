# Gym Tracker

Personal workout-tracking PWA — strength & hypertrophy, progressive-overload suggestions, offline-first, cross-device sync. Single vanilla-JS file, no framework, no build step. UI in Portuguese (pt-BR).

**Live:** https://pbbabreu.github.io/gym-tracker/

## Features

- **Treino** — log workouts from reusable plans or free-form; adding an exercise opens a **movement-first picker** built on three levels — exercise = what you *track*, movement = what you *plan*, family = what you *browse*: families group related movements ("Supino" holds reto and inclinado; "Terra" nests a "Sumô" subfamily, with a *Ver todos* flatten), muscle chips filter by **involvement** (a movement or family shows under every group it works, with a "Também envolvem" section), and a movement's variants group by equipment class. Bilingual search reaches families, movements and exact variant names; new variants created inside a movement inherit its classification and a chosen equipment class. An exercise created mid-session asks for its muscle group and movement pattern up front (an unclassified one would be invisible to the per-muscle volume chart), and every block carries a note for how it actually went today — “banco 7”, “ombro incomodou” — saved with the session and read back in Histórico. Warm-up sets are auto-generated and scaled to today's suggested working weight (a first-ever exercise asks for an estimate and prefills warm-ups *and* work loads from it; barbell warm-ups never drop below the empty bar; an isolation exercise's single warm-up prescribes light-step reps at its 50% load). Strength/hypertrophy is a per-session tracking mode — each exercise defaults to the mode of its *last* session, not a stored label — and so is **unilateral execution**: a *Uni* toggle on the block (and a default in the Library) marks one-side-at-a-time work without needing a separate variation, keeping its progression history, suggestions and PRs apart from the bilateral ones — a single-side 40 kg never competes with a two-sided 80 kg. Exercise blocks collapse into a focus mode: an exercise-level ✓ (or checking every set) folds the finished block and opens the next one. The in-progress session survives closing the tab, the Back button, or the OS killing the page — it's continuously mirrored locally and restored on the next open; tapping a prefilled reps/kg field clears it for fresh typing (leaving without typing restores it), and the browser Back button closes open dialogs instead of leaving the app.
- **Equipment & machines** — every session block carries a 🔧 chip naming the *specific* apparatus: machines/cables are **calibrated** (suggestions prefer that same machine's history — numbers from one unit never masquerade as another's; a save-time nudge asks about unidentified machines, never blocking), while free-weight equipment is **descriptive** (the bar tells you what you did the movement with; progression stays one story). Machines remember settings notes ("banco 7, pegada aberta"), belong to gyms with one-tap reuse elsewhere, and auto-attach from last time. A ✎ on every machine (in the 🔧 picker and the exercise detail view) edits or deletes it — renames keep history's snapshots, deletes never touch logged sessions — and the progress chart can filter its series per machine, defaulting to the one in current use. A dismissible line at session start points out calibrated blocks still missing their machine. Barbell blocks add a ⚖ setup: bar weight + how loads are typed — **Total, Por lado, or Anilhas** — with a computed Total column, "barra vazia" at zero, and storage always as the grand total so history and charts never change units.
- **Supersets** — group 2+ exercises into rounds, assembled in the plan editor or mid-session (⛓ *Novo superset* opens a builder that can add exercises from inside itself). Rounds interleave the members' sets (a→b→c, next round, …) with unequal set counts handled naturally — a member with fewer sets just sits out the later rounds. Rests are the group's own: a default between exercises and another after each round, each individual gap editable in place as a row in the round table. Warm-ups are done per exercise before the rounds by default, or ride the rounds via a group-level switch — and a member can be on a warm-up while another works. Finishing a round folds it, opens the next and starts the between-rounds rest; members can be reordered per round (promotable to all rounds). **Progression stays per exercise** — a superset is how you train, not how progress is measured — so history, suggestions and charts are untouched; Histórico shows the grouping as a ⛓ bracket over the individual exercises. *Desagrupar* dissolves a group back into ordinary blocks, and grouping travels with shared plans.
- **Rest timer** — checking a set starts a countdown sized by the transition (warm-up→warm-up / warm-up→work / work→work), with presets and custom values resolving per exercise → per plan → per exercise default → device defaults. Beep on expiry; vibration too on Chromium-based Android browsers (Chrome, Edge, Samsung Internet — Firefox removed the Vibration API in 2024, and iOS never had it).
- **Progressive overload** — set rows suggest a genuine next-session target, not a replay of last time: an exercise "graduates" to more weight only when the full prescribed set count hit the top of the rep range at one working weight (strength 3×3–5, hypertrophy 1×6–10/12). Fatigue drop-offs don't graduate; multi-session stalls get a visible nudge. **Timed exercises progress too**, on whichever axes they have: a loaded hold clears a seconds band and then the load goes up (target resetting to the band floor), while a bodyweight hold — which has no load to add — simply gets longer, the bar tracking your last hold so it never stalls once you pass the band.
- **Gym profiles** — mark which gyms have which exercises; starting a plan at a gym flags what's unavailable and suggests equivalent swaps (same muscle + movement pattern). A ⇄ on every session block swaps any exercise for an equivalent, ranked candidates first with anything unavailable at the current gym dimmed and pushed down rather than hidden (a stale tag must never hide the exercise you're trying to fix) — and when the block already holds typed sets, it asks whether to **keep them** (you logged the work under the wrong exercise — the numbers are right, only the label was wrong) or **start fresh** (you're genuinely doing a different exercise), warning when the regime or reps-vs-seconds measurement differs. *+ Nova variação* right in the swap list creates the missing variant on the spot, inheriting the current exercise's full classification and keeping the sets.
- **Plans ↔ sessions** — a plan entry is either a fixed exercise or a **movement slot** ("Remada baixa — qualquer variação"): the actual variant is picked at session time through a ranked chooser (📌 remembered-for-this-gym, last-done-here, **★ favorites**) with a one-tap *Usar* on the suggestion — never auto-picked. Entries carry optional prescription notes ("pegada aberta, 3s excêntrica"), the same exercise can appear twice, and entries can be **grouped into supersets** right in the editor (lettered ⛓ groups with their own rest defaults, carried into the session and along with shared plans). Plans carry per-exercise rest timings; a session started from a plan can drift freely, and saving offers to update the plan (slots stay slots — the plan keeps its intent), fork a new one, or keep the plan untouched. Any saved session (or a free workout, at save time) can be turned into a plan.
- **Sharing** — send a plan to another user by e-mail in-app (appears under *Planos recebidos*), or as a self-contained JSON file; re-sync seeded exercises to the current curated names and content with **⟳ Nomes** (confirmed, listed old → new; history, plans, machines and your own creations untouched — and it propagates to your other devices).
- **Histórico** — past sessions with per-set detail, volume, gym tag, duration (shown only when trustworthy — logged the day it happened, a plausible length) and edit/delete/extract-to-plan. A session that set a personal record gets a 🏆 badge and a prev → new summary — checked on every save, on an honest metric per regime (weight + estimated 1RM, lowest assisted counterweight, most reps, longest hold), against everything up to that session's own date so a workout logged after the fact still compares fairly.
- **Biblioteca** — the curated, PT-BR-primary exercise library (English names and aliases kept searchable) is **delivered with the app and stays current on its own** — new curated exercises simply appear, and **none of it requires an account** (signing in buys remote backup and sharing, nothing else). Exercises you delete stay deleted, and a ↩ Excluídos dialog restores them if you change your mind. Your own creations live alongside the catalog and are never touched by it, classified by muscle group + movement pattern + **movement** (the family a variant belongs to) + an equipment class editable in place, and with a detail view carrying cues, common errors and known machines (editable from right there). Every exercise says where it came from — the curated catalog, **you** (“Minha”), or a plan someone **shared** with you (“De …”) — one identical shape for all three, with only the origin differing; the catalog refresh can only ever touch catalog entries. Exercises measured in **time** rather than reps (planks, dead hangs) are marked as such: their set column counts seconds and durations read as m:ss. They progress on time — a bodyweight hold gets longer, a loaded one clears its seconds band and then gains load — while estimated 1RM and volume-load, being rep-based, stay off for them. Duplicate entries are prevented at creation (matching Portuguese *and* English names) and, if any exist, can be reviewed and merged — duplicates split an exercise's history, which quietly degrades suggestions and progress charts.
- **Peso** — bodyweight log; feeds real-load math for the two regimes that lean on it: **assisted** (bodyweight − counterweight) and **BW+** (bodyweight + added load — weighted pull-ups, dips, dead hangs), plus plain bodyweight.
- **Conta** — an at-a-glance status tab: login state, an honest answer to *"is this device in sync with the cloud?"* (em dia / changes waiting to upload / failing / frozen — derived from the sync machinery's own state, with a ↻ sync-now button), what this device holds per collection, and the **app version**, so you can tell whether an update has reached this phone. Read-only by design — the actions live in Backup & Sync.
- **Sync & backup** — invite-only account sync (magic link / code); manual JSON export/import; automatic daily local snapshots (last 7 days, restorable in-app); a factory reset that wipes everything and rebuilds the library clean across devices; legacy GitHub Gist driver for pre-account installs.

## Using it

Just open the live URL in your browser — that's the supported way to use it, on every platform. It works offline after the first load (the service worker keeps the offline copy current with your last online visit), and a home-screen shortcut that opens a browser tab is a perfectly good "app icon".

> Installing as a standalone PWA also works on Android, but is deliberately not the recommended path for now: on iOS, login e-mail links open in Safari — *outside* a standalone app — which strands the session. Browser usage sidesteps that entirely. (A type-in login code that fixes standalone iOS exists in the app and activates once custom SMTP is configured for the project.)

## Cross-device sync setup

**Account sync (default):** open the **Conta** tab → *⚙ Backup, login e restauração* (or **Histórico → ⬆ Backup & Sync** — same place), enter your e-mail, and tap the magic link that arrives — no password exists. (The app also has a 6-digit-code field, which activates once the project's login e-mails carry a code — pending custom SMTP setup.) Your data syncs to a private per-user store (Supabase, guarded by row-level security); logging in on another device pulls and merges your history before anything is ever pushed, so a fresh phone can never overwrite it. Accounts are invite-only: the instance owner adds new users.

**Onboarding a new user:** the owner invites their e-mail (Supabase dashboard → Authentication → Users → Invite). The person opens the app URL in their browser, goes to Backup & Sync, enters that e-mail, and taps the login link they receive. From there they can be sent workout plans in-app (✉ on any plan → appears under *Planos recebidos*). The exercise library itself needs no invite — it ships with the app and keeps itself current, so anyone can just open the URL and train; an account only adds remote backup and plan sharing.

**Legacy Gist sync:** earlier installs synced via a private GitHub Gist (fine-grained PAT with gists-only scope). That driver still works and remains available on devices that configured it, until they migrate to an account. New installs never see it.

Data notes:

- All workout data lives in your browser's localStorage and your own private sync store — nowhere else. Login/config state is stored locally only and is **never** included in exports.
- Merging is per-item last-writer-wins with deletion tombstones, so devices can be used independently — even offline — and converge safely.
- The app additionally keeps rolling daily local snapshots (last 7 days), restorable from the Backup & Sync modal.

## Development

No build step — `index.html` is the app.

```
python -m http.server 8742        # from the repo root
```

- Develop against `http://localhost:8742/` — `file://` breaks reloads and service workers.
- **Tests:** open `http://localhost:8742/tests/run-tests.html` — a self-contained regression suite (724 checks) that loads the real app in an iframe and asserts against the shipped functions. Run it before every push. It wipes the origin's storage: local server only, never the live origin.
- **Version marker:** `APP_VERSION` in `index.html` (shown on the Conta tab) is hand-bumped on every push that changes `index.html` — there is no build step to stamp it. Date + letter for same-day pushes. Its whole job is answering "did the deploy reach this device?", so a push without the bump makes it lie.
- Service-worker gotcha: if an edit doesn't seem to take effect, the SW may be serving cache — unregister it and hard-reload (the test runner does this automatically).
- `supabase/` holds the canonical database SQL (01 = per-user storage, 02 = sharing tables, 03 = generated catalog seed, 04 = machines-collection migration); `.github/workflows/keepalive.yml` pings the project weekly so the free tier never pauses.
- **The exercise catalog is not authored in this repo.** `library.json`, `supabase/03-catalog-seed.sql` and `SEED_CLASSIFICATION` are build output of `python tools/build-library.py`, which reads curated exercise notes from a separate Obsidian vault. Run `python tools/build-library.py --check` before pushing — it validates the catalog and fails if the committed artifacts drift from their source.
- Deploys are just pushes to `main` — GitHub Pages serves the repo root (~30s).
